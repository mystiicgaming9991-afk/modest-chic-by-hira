# Commerce integration review

Reviewed 2026-10-25 against the draft specifications in `backend/specs/`, source code, unit/contract/integration tests, and the Next.js production build. A specification file or database table does not establish that its workflow is implemented.

## Verified path

- Published product and live stock appear in the storefront; the configured API is the source of product prices and availability.
- A browser guest can add an item, read the persistent cart, choose a configured service city, obtain the current COD quote, accept the displayed policy, and place an order through the Next.js BFF and live API. A local browser journey reaches the private confirmation page; PostgreSQL verifies the accepted order, payment state, active reservation, reduced available stock, and cleared cart.
- The order transaction creates item snapshots, a stock reservation, a COD payment attempt, and an access credential. Exact request replay returns the same order; changed replay conflicts.
- The local smoke journey used a disposable seeded database and produced order `MC-20261024-0001` with a PKR 1,000 item, PKR 250 delivery charge, and PKR 1,250 accepted total. This is test evidence, not a production order.
- The staff proxy completed test-account login, authorized identity and staff list reads, refresh rotation, and logout. Browser staff pages cover sign-in, invitation acceptance, password recovery, authenticator enrollment, and owner staff access controls. The proxy keeps access and refresh credentials in separate HttpOnly cookies.
- Staff with `notification.read` can inspect paginated status for authentication/system email outbox events. The query excludes encrypted payloads and the response omits recipients, message content, and aggregate IDs. This does not enable transactional order messaging or stale credential retries.
- An authorized staff test account recorded a COD contact attempt and confirmed the smoke order. The buyer's private page then showed `confirmed`. An integration test covers confirmation stock retention, decline stock release, and repeat-decision rejection.
- Database migrations upgrade and downgrade through all revisions on a clean PostgreSQL database. The full backend suite passed with dedicated test, migration, and bootstrap databases.
- The canonical Compose configuration now contains PostgreSQL, Redis, API, and worker services. Local Compose defaults satisfy settings validation; the API image checks readiness, and the health contract verifies that dependency loss returns 503 while liveness stays available. These are local checks only; production traffic gating and restore recovery remain unverified.
- The deployment recovery procedure was smoke-tested with matching PostgreSQL 16 client tools: a custom-format backup restored into a new isolated database, Alembic reported revision `0020_builtin_role_grants`, and all five built-in role rows matched. This does not verify production backup coverage, private objects, retention, checksums, or recovery timing.
- Customer email OTP now creates or signs into a unique verified-email account, with normalized addresses, request and verification throttles, resend supersession, expiry, five-guess exhaustion, and revocable sessions. The API returns an HttpOnly-cookie-safe session result through the Next.js BFF; staff and customer credentials remain separate.
- Staff with `customer.manage` can suspend or re-activate a verified email account from the customer workspace. Suspension revokes every active customer session, status edits require the version loaded by the staff page, and each change is audited; re-activation does not restore old sessions, so the customer must request a fresh email code.
- Signed-in customers can inspect and withdraw a previously recorded marketing email consent from the account page. Withdrawal appends one source-attributed consent decision, preserves its policy version, and is idempotent; this is an opt-out only, and marketing messages/exports remain disabled pending approved language and enforcement integration.
- Signed-in checkout links orders to the verified customer. Guest orders stay unlinked until claimed with that order's private credential; history only lists linked orders. Integration tests cover guest separation, claim proof, replay, logout, and ending other sessions.
- The frontend has an account page for OTP login, order history, and session controls, plus order-claim UI on the private confirmation page. Account browser coverage exercises requesting and verifying an email code while keeping guest checkout available; BFF coverage verifies the session token is exchanged for an HttpOnly cookie, omitted from JSON, and forwarded to the identity API only as `X-Customer-Token`.
- Guest checkout resolves phone/name identities under a transaction advisory lock and assigns each accepted order to a customer profile. Concurrent same-identity checkouts converge, while conflicting names on a shared phone remain separate.
- Staff customer search, linked-order history, and reusable address reads are connected to the customer workspace. Address creation is shown only with `customer.manage`, passes through the CSRF-protected staff BFF, and records the staff actor. Consent writes remain API-only and require the same permission.
- Coupon codes now flow through the storefront quote and order acceptance. Eligibility checks cover active windows, usage and per-customer limits, minimum order, product/category scope, maximum discount, and exact per-line allocation. Redemption usage is reserved atomically with order creation, consumed on COD confirmation, and released on decline or stock expiry. The checkout summary displays savings and binds acceptance to the applied code. A permission-gated staff form now creates promotions; timezone inputs are validated at the API boundary.
- Promotion staff workflow now includes listing and editing existing codes, active/paused control, and product/category pickers. API reads require `promotion.read`; creation and edits require `promotion.write`.
- A real PostgreSQL checkout journey now verifies coupon quote savings, the accepted order and order-line discount, payment amount, exact replay, and a single reserved redemption.
- Staff manual sales now use current published catalog prices, configured delivery/pickup settings, locked stock, customer-profile resolution, COD payment records, a source and attribution snapshot, and an idempotency key. The PostgreSQL checkout journey verifies a SOCIAL order, linked profile, creator/campaign attribution, and exact replay.
- Staff can search orders by number or customer context, filter by state/source/date, and inspect accepted item/contact/address snapshots, ordered events, separate payment attempts, and available shipment/pickup/return/refund records through a permissioned admin screen.
- Authorized pack staff can move a confirmed order into processing through a row-locked, idempotent command. It requires sufficient active, unexpired reservation coverage; order detail exposes the action only for a confirmed, covered order, displays an exception otherwise, and records an actor event without changing payment or claiming shipment/delivery completion.
- Authorized pack staff can record a delivery shipment allocation after processing and payment eligibility checks. Quantities are bounded by unfulfilled order quantities and active reservations; a stable merchant reference and shipment event are persisted. Exact retries replay, changed-payload key reuse conflicts, and the order detail screen distinguishes packing from courier booking.
- Authorized fulfillment staff can hand off a fully packed delivery order. The command verifies COD confirmation or online payment eligibility, checks that shipment allocations and active reservations match every remaining order quantity, consumes stock with the staff actor, marks shipments handed off, and fulfills the order atomically. Exact retries replay. The order detail screen enables the action only when every remaining item is packed.
- Staff with `order.cancel` can cancel a pending, confirmed, or processing order only before fulfillment effects have progressed and while payment remains pending or failed. Cancellation requires a reason and idempotency key, releases active reservations and eligible coupon use once, marks unhanded packed shipments and uncollected pickups cancelled, and retains an actor event. The order screen exposes the action only when these conditions are met.
- COD contact attempts require an idempotency key; exact retries return the prior order result and changed details conflict instead of duplicating contact history. The queue UI retains the key after an uncertain request so a retry is safe.
- Staff with `analytics.read` can review an attribution report grouped by the accepted source, campaign, creator code, and order source snapshots. It reports order intake, current order-state counts, and customer discount totals separately; it explicitly does not present placed COD value as collected revenue. Date boundaries are UTC and cancelled orders remain in historical intake counts.
- The staff home now shows a permission-gated current order-state snapshot and links each state to the filtered order list for staff with `order.read`. Financial summary output is disabled until payment and refund records can support reconciled figures; lifecycle counts are labeled as current-state counts rather than daily sales.
- The staff dashboard now adds exact COD-confirmation, stock-reservation-exception, packing, pending-review, and inventory counts only when the current identity has the corresponding permission. Each linked queue has a matching list filter; the stock exception queue finds pending COD orders and fulfillment-eligible orders whose outstanding quantities are not fully covered by active, unexpired reservations. Pending COD cards also show this condition and block confirmation while it holds; the packing queue includes only processing delivery orders with eligible payment and remaining units to pack. Inventory views use stable offset pagination.
- Purchase reviews are now connected end to end: an eligible private order page submits against its order-item ID using the HttpOnly order credential, pending reviews require permissioned staff moderation with a reason and audit entry, and product pages expose only approved reviews with approved-only aggregates and stable cursor pagination. Browser tests cover public review display and the staff moderation permission/reason flow.
- The private guest order page now shows a chronological buyer-safe lifecycle timeline from allow-listed order events. It omits free-form event metadata, internal contact notes, actor identities, and unknown event types.
- Signed-in customers now see the same safe lifecycle milestones in linked account order history. The service fetches events in one bounded query for the 100 most recent linked orders, avoiding one query per order.
- Product and collection pages now generate titles, descriptions, Open Graph metadata, and canonicals from published catalog data when the configured site URL is available. Unknown/unavailable catalog pages and personal account, cart, wishlist, checkout, order-confirmation, and staff routes are excluded from indexing.
- Live storefront shipping and returns pages fetch the current effective policy through the commerce BFF; preview mode shows preview copy without making an API request. - A local browser smoke check at the responsive shop viewport added a preview product, verified its cart summary, and followed the preview-checkout link. ## Review findings fixed

- A new password-reset request left earlier unused reset links valid. New requests now consume prior unused links in the same transaction, and reset issuance/consumption lock staff rows before reset rows to avoid lock inversion. The regression proves an older email link fails after a newer request while the latest link changes the password; the auth requirements and convergence evidence now specify this behavior.
- Audit metadata was described as allow-listed but accepted nearly every key except a short exact deny-list. The repository now keeps only fields registered for the specific action, drops nested or oversized values, and stores no metadata for unknown actions; focused unit tests cover attempted password, reset-link, nested-secret, and unregistered-field injection.
- The frontend test toolchain used vulnerable Vitest 2.1.9 dependencies and resolved Vite 5 despite the React plugin requiring Vite 8. Upgraded to Vitest 5.0.5, Vite 8.3.5, and compatible Node types; retained the prior mock-history behavior, declared the required Node versions, and moved the Vitest config to native ESM. All 160 browser tests, lint, TypeScript, and the production build pass. `npm audit` and `uv audit` report no known dependency vulnerabilities; `uv audit` is experimental.
- The owner settings page refetched all settings when a different setting was selected and allowed out-of-order policy responses to replace the current selection. Settings now load once after authorization, policy responses are guarded by both type and request generation, and editors/navigation are locked during saves. Browser tests cover permission gating, versioned setting writes, secret masking, single-load selection, stale policy responses, and locked controls during an in-flight write.
- Manual order entry only loaded the first 100 published products, generated a new idempotency key for every attempt, and showed a sign-in message when the staff API was unavailable. The form now follows catalog cursors, reuses the key for an unchanged request, refuses changed details while an earlier request may have succeeded, applies the backend's per-line quantity limit to the combined variant quantity, and shows service errors without misclassifying them as sign-in failures. Browser coverage verifies cursor loading, retry replay, edited-retry blocking, and the service-outage state.
- Promotion product scopes also loaded only the first 100 published products. The staff promotion form now follows the catalog cursor so later products remain available when creating or editing scoped coupons; browser coverage verifies the next page appears in the eligible-product list.
- Staff workspaces redirected to sign-in for any identity API error, including service outages. The staff client now retains HTTP status on API errors, and workspace gates redirect only on 401; other failures stay visible as service errors. Authenticator enrollment now also exits its loading state on an API failure. Browser and helper tests cover the outage classification.
- If a protected staff request received 401 while the refresh endpoint was unavailable, the client kept the original 401 and still sent users to sign-in. It now propagates a non-401 refresh error and preserves 401 only when the refresh credential itself is rejected; client tests cover both cases and retained HTTP status.

- The published shop's above-the-fold campaign image was lazy-loaded and triggered Next.js's LCP warning during the browser smoke. It now uses eager loading so it can render promptly when visible.
- Collection pages could select a later image in the visible product row as LCP while it was still lazy-loaded. The first grid row now loads eagerly, only its first image is preloaded, and a component regression test covers eager loading. A fresh collection browser smoke no longer reports the warning.
- Above-the-fold home and product images used the deprecated Next.js 16 `priority` prop; they now use `preload` as documented for the current Image component.
- A product-page browser visit flagged its above-fold catalog image as lazy because the same source also appeared in a lazy-loaded image thumbnail. The hero image now uses the explicit eager hint alongside preload, and its visible selected-photo thumbnail is eager; a fresh local browser visit no longer reports the LCP warning.
- The commerce proxy forwarded every exported HTTP method to each allow-listed path, including writes to public read-only policy/catalog routes. It now matches methods to the actual API contracts and returns 405 with an `Allow` header before forwarding unsupported methods.
- The staff proxy had the same method gap and grouped the read-only staff directory under the authentication route set. It now enforces backend route methods, keeps `/admin/staff` as GET, and restricts unsupported writes before CSRF setup or upstream forwarding.
- The catalog group editor sent POST for collection product ordering and product category/tag membership replacement, while the API requires PUT. All three frontend mutations now send PUT and have a regression test covering the outgoing methods.
- The foundation and catalog quickstarts had stale migration/API instructions. They now use the current migration head and method/version/CSRF requirements, and clarify that the catalog media endpoint only attaches existing object metadata rather than uploading files.
- The catalog API's existing-media endpoint was not exposed by the staff BFF or catalog UI and did not create the audit event required by the catalog plan. The staff form now attaches existing object keys and accessibility metadata; the backend validates variant ownership, replaces the previous primary image transactionally, and records the actor. On published products, media metadata is visible in the public catalog API, while the storefront still renders local `/images` assets only. Proxy, browser, API contract, and PostgreSQL audit/primary-replacement tests cover the workflow; upload and external delivery still require configured storage.
